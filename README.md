# Демо: OpenSpec против чистого вайбкодинга

Сравнение двух подходов к одному и тому же изменению в одном и том же репозитории, одним и тем же агентом, по одному и тому же промпту. Агент — Claude Code, модель `glm-5.3`, medium effort. Берём работающий сервис бронирования переговорок и меняем в нём контракт API: бронь теперь может занимать несколько комнат. Дважды — «голым» вайбкодингом и через OpenSpec.

Этот лист скрыт от агента до разбора. По нему ведущий отвечает на вопросы агента, по нему же написаны внешние приёмочные тесты.

Основной репозиторий https://github.com/vyhuholl/openspec-demo-new

Ветки:

Название | Содержимое
--- | ----
`master` | базовый сервис бронирования
`spec` | он же + настроенный OpenSpec, конституция проекта и спека текущего поведения сервиса (`openspec/specs/bookings`). В конституции есть карта критичности требований.

Код сервиса в ветках одинаковый. От `master` пробуем внести изменение чистым вайбкодингом, прогоняем приёмочные тесты, смотрим на результат. Затем — то же самое через OpenSpec от ветки `spec`.

## Промпт

Один и тот же для обеих веток. В ветке `spec` подаётся через `/opsx:explore`.

```
Бронь теперь может занимать несколько комнат сразу — например, две смежные переговорки на общую встречу.

POST /bookings
{
  "rooms": ["green", "blue"],
  "start": "2027-11-01T09:00:00Z",
  "end":   "2027-11-01T10:00:00Z"
}

201: {"id": "...", "rooms": ["green", "blue"], "start": "...", "end": "..."}
Брони в ответе GET /bookings — в том же формате.
GET /bookings?room=green&date=2027-11-01 возвращает все брони, в которых есть комната green.
Остальные коды ответов — по сложившимся в сервисе соглашениям.

Покрой тестами, как принято в репозитории.
Готово, когда make ai-check зелёный.
```

## Ответы на вопросы агента

- Отвечать на вопросы агента только по этому листу и одинаково в обеих ветках. Vibe-агент тоже может спросить — отвечать ему так же.
- Отвечать на заданный вопрос, не выдавая соседние пункты: спросили про лимит — не рассказывать про старых клиентов.
- Вопроса нет в листе → «На ваше усмотрение, зафиксируйте как допущение». Приёмка такие места не проверяет.
- Агент предлагает варианты и просит выбрать → выбрать тот, что совпадает с листом; если ни один не совпадает — ответить по листу.
- Ничего не сообщать без вопроса.
- Допущение, которое агент явно вынес на подтверждение («возразите — поправлю»), считается вопросом: отвечать по листу.
- Допущение, которое только записано в proposal без явной просьбы подтвердить, вопросом не считается.

**Q1. Старые клиенты.** Старую версию мобильного приложения обновят только через квартал. Она шлёт `room` и читает `room` из ответов POST и GET — до обновления у неё всё должно работать как раньше:

- запрос с `room` вместо `rooms` — бронь на одну эту комнату, по прежним правилам;
- в ответах POST и GET у каждой брони оба поля, `rooms` и `room`: `room` — первая комната из `rooms`, `rooms` — в том порядке, в каком пришли в запросе;
- `room` и `rooms` в одном запросе — 400, ничего не создаётся.

*(Вопрос вида «подтверждаете, что room убираем из API?» — это Q1, отвечать им целиком.)*

**Q2. Конфликт.** Если хоть одна из комнат занята на пересекающийся интервал — 409 на всю бронь, ни в одной комнате ничего не создаётся. Касание (конец одной = начало другой) — не конфликт, как раньше.

**Q3. Повторы.** Одна и та же комната дважды в `rooms` — 400, ничего не создаётся. Комнаты сравниваются как раньше, с учётом регистра: `green` и `Green` — разные комнаты.

**Q4. Лимит.** Не больше 5 комнат в одной брони: больше пяти смежных переговорок в офисе нет. 6 и больше — 400.

**Q5. Невалидный rooms.** Пустой массив, `null`, не массив, элемент не строка, пустая строка или одни пробелы — 400, ничего не создаётся.

## Запуск приёмочных тестов

Из корня этого репозитория:

```bash
./judge.sh <путь к основному репозиторию>
```

Скрипт собирает `cmd/booking`, временно кладёт тесты в `<repo>/acceptance/` и после прогона удаляет. В конце показывает, сколько строк агент удалил и добавил в тестах, которые были в ветке до его работы, и путь к полному diff: так видно, как агент переписал старые тесты под новый контракт.

## Что проверяют приёмочные тесты

Курсивом выделены тесты, на которых вайбкодинг-решение стабильно ломается.

| Тест | Пункт | Типовая ошибка, которую ловит |
|---|---|---|
| *TestBase_SingleBooking* | база, Q1 | запрос старого клиента с полем `room` получает 400 |
| TestRooms_CreatedAndListed | промпт | бронь не видна в выдаче одной из своих комнат; вместо одной брони — по брони на комнату с разными id |
| *TestLegacy_OldClientRequest* | Q1 | `room` заменён на `rooms`: запрос старого клиента — 400 |
| *TestLegacy_ResponseKeepsRoom / single_room_via_rooms* | Q1 | из ответов POST и GET пропало поле `room` |
| *TestLegacy_ResponseKeepsRoom / old_client_request_gets_rooms_too* | Q1 | в ответе на запрос старого клиента нет `rooms` |
| *TestLegacy_ResponseKeepsRoom / room_is_first_of_rooms* | Q1 | `room` в ответе — не первая комната из запроса |
| TestLegacy_ResponseKeepsRoom / rooms_keep_request_order | Q1 | `rooms` пересортированы |
| *TestLegacy_RoomAndRoomsTogether* | Q1 | одно из полей молча побеждает |
| *TestLegacy_ConflictWithMultiRoomBooking* | Q1 | брони старых и новых клиентов не видят друг друга |
| TestRooms_Conflict_WholeBookingRejected | Q2 | бронь создаётся в свободных комнатах, занятая молча пропускается |
| TestRooms_DuplicateRooms / same_room_twice, repeat_among_others | Q3 | повтор комнаты молча схлопывается |
| TestRooms_DuplicateRooms / different_case_is_a_different_room | Q3 | `green` и `Green` считаются одной комнатой |
| *TestRooms_Limit* | Q4 | лимита нет или граница сдвинута |
| TestRooms_InvalidRequest | Q5 | мягкая валидация `rooms` |

## Выводы
* Чистым вайбкодингом агент стабильно ломает старый контракт и переписывает тесты, которые его охраняли (а если и задаёт вопросы, то про косметику). Через OpenSpec видит, что старое поведение зафиксировано в спеке, и спрашивает, нужно ли сохранять совместимость.
* Там, где агент задал вопрос во время `/opsx:explore`, код правильный в 100% случаев.
* Каждая ошибка в spec-ветке — незаданный вопрос, и он виден в `proposal.md` как допущение ещё до кода.
* Даже если работаете без OpenSpec — как только задача становится хоть сколько-нибудь сложной, нужно обсуждать с агентом реализацию фичи *до* написания кода.
